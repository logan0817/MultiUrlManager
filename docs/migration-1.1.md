# 从 1.0.x 升级到 1.1

本说明针对当前开发版。包名与 Maven 坐标保持不变；真实 Maven Central 1.0.6 AAR 的 17 个公开类、105 个字段/方法已与当前 Release AAR 对比通过，证据与检查范围见 [API 基线](api.md#已发布二进制兼容基线)。这保证已检查的 JVM 入口保留，不意味着行为无变化；实际消费、页面、数据和两个 API 端点仍需分别验证。

## 有意行为变化

| 旧用法 | 1.1 行为与替代 |
| --- | --- |
| 直接修改 `dynamicUrls` 或其中对象 | getter 返回隔离副本；使用快照加 `saveAsync`，或显式调用旧 updateBaseURL |
| 固定 JSON 中的 debug_defaults / release_defaults，未指定键时依赖库的 DEBUG | 固定 JSON 仍支持；新格式可写 defaultEnvironment，显式 Builder 设置优先，均未指定时回退 release_defaults |
| 新增立即落盘，页面选择稍后保存 | 页面所有操作使用草稿，保存统一提交，取消放弃 |
| 全量更新先清空再逐条写入 | 复制输入、完整校验、整体持久化 |
| 同组允许多个选中项 | 批量数据拒绝多选；单条显式选择取消组内其他选择 |
| 任意协议或地址字符串 | HTTP(S) 校验，禁止认证信息、query、fragment，补尾斜线 |
| 写入失败没有结果 | 新入口返回原因，旧写入入口抛异常 |
| clear 后自动恢复默认 | clear 明确清空，恢复默认使用独立操作 |

快照中的 BaseUrl 为兼容仍可修改，但内部管理状态不会随副本变化。旧列表行为收紧会影响依赖隐式修改的调用方，升级前检索 `dynamicUrls` 的写入点。

## 旧数据迁移

### 升级后究竟使用哪一套地址

| 安装或升级场景 | 启动后生效的数据 | 新版默认配置如何处理 |
| --- | --- | --- |
| 首次安装，没有新旧存储 | JSON defaultEnvironment 或宿主显式指定的默认环境 | 使用当前 JSON 或代码定义；均未指定时兼容回退 release_defaults |
| 从 1.0.x 覆盖安装，存在有效旧记录 | 迁入 `legacy` 历史配置，并继续使用旧选择 | 新版环境同时提供，但不会自动切换过去 |
| 旧记录只是旧版自动写入的默认地址，从未手动修改 | 仍按旧记录迁入 `legacy` | 旧版没有保存默认定义与用户修改的区别，无法可靠识别，因此不自动替换 |
| 已使用新版快照，随后更新内置默认定义 | 保持当前环境，按下文规则合并 | 未修改的业务组跟随新默认，修改过的组保留用户选择 |
| 旧存储为空，且没有新版快照 | 宿主默认环境 | 旧版未初始化和主动清空无法区分；不能从空偏好恢复旧选择 |
| 全部旧记录无效，或新版快照损坏 | 初始化失败，保留原文件 | 不静默覆盖成默认服务器 |

“兼容旧数据”表示有效旧候选、业务键、备注和选择可以延续；不表示旧版默认地址会自动转换成新版 `dev` / `test`，也不表示旧业务键自动改名。须在相同应用数据空间内覆盖升级；卸载、清除数据、变更 applicationId 或签名不能作为数据迁移验证。

例如，旧 Demo 的 `searchApiDomain → https://www.google.com/` 和 `gitDomain → https://www.github.com/` 会继续以原业务键保存在历史配置。新版 Demo 的 `order`、`login` 是另一套演示业务，调用 `getUrl("login")` 不会自动映射到旧的 `gitDomain`。要体验新案例，进入管理页显式选择开发联调或测试验收环境并保存；旧历史环境仍保留，可再次切回。

新状态位于应用内部 `files/multiurlmanager-state.json`，通过 AtomicFile 整体替换。新文件不存在且旧 `dynamic_base_urls_config` 非空时迁移：

1. 独立解析旧记录，跳过无法解析/校验的记录；有效记录按 time、URL 稳定排序。
2. 按规范化后的 configKey + URL 去重，同地址优先保留已选中的原记录及其备注、时间；再按 time、URL 排序，同组多选保留首个选中项。
3. 导入“历史配置”环境并设为当前环境，不猜测旧地址所属环境。默认 id 为 `legacy`；若宿主已占用，则依次选择 `legacy-1`、`legacy-2` 等首个可用 id，保留全部宿主默认环境。
4. 新状态成功写入后使用它；原 SharedPreferences 保持原样，作为迁移前备份。

覆盖升级回归位于 `fixtures/upgrade`：旧阶段使用真实 Maven Central 1.0.6 AAR（固定摘要），固定 JSON 来自 `801d130`；Debug 选择 `debug_defaults`，Release 选择 `release_defaults`。旧库实际初始化并写入 SharedPreferences，随后同 applicationId、同测试证书覆盖安装当前库，核对全部候选字段、旧偏好备份、新默认环境与生效映射，并再启动一个新进程验证幂等。另覆盖用户自定义选择/备注及旧 Demo 实际代码 provider 的 `videoApiDomain` / `mailDomain` 数据。旧业务键不自动映射成 `order` / `login`，Release 默认 production 不会覆盖已有 legacy 选择。

这些测试使用隔离夹具和测试证书，不能代替业务宿主正式签名包的分发验收。2026-10-16 仅构建旧 Debug/Release APK、提取 asset 并手写偏好的证据，不应表述为完整生产包覆盖升级。当前执行结果以 [开发验收记录](development.md#发布前本地审核记录) 和同提交 CI 为准。

所有旧记录无效时初始化失败，避免静默切换默认服务器。需要宿主提供明确恢复入口或在可控调试环境备份后恢复。遇到损坏的新状态文件也不会以空配置覆盖；保留文件用于诊断。

## 默认配置升级与恢复

状态快照同时保存上版默认定义，初始化时按业务键比较当前候选与上版默认：

- 一组候选的 URL、选择和备注仍与上版默认一致时，整组跟随新版默认，包括移除的默认组。
- 用户改过的一组保留现有候选和选择；新版新增候选作为未选中项补充，不抢占用户选择。
- 新增业务键和环境补齐；用户明确删除的一组及明确清空的环境保持空，不在重启后偷偷恢复。
- 不再出现在默认定义中的自定义环境保留。原默认组被用户修改后，即使维护者删除其默认定义，用户数据仍保留。

当前环境默认值通过 `defaultEnvironment(id)` 查询。迁移生成的历史环境（`legacy` 或避让冲突后的 id）没有对应宿主默认定义，不能直接恢复为猜测的默认环境；先显式切换宿主定义的环境。恢复默认会丢弃该环境的自定义候选，在页面确认后保存。clear 保留必选声明并清空全部环境候选，不能作为恢复默认的替代调用。新增默认键、默认升级、覆盖和显式清空仍需回归与设备证据，见 [实现验收清单](plans/v1.1.0-implementation-plan.md)。

默认配置跟随更新要求环境 id 与业务键保持稳定。改名等同于新增定义，不能推断为原有环境或业务的迁移。合并需要此前快照中保存的默认定义；缺少该定义时已有环境保留原数据，只补充新环境。新增必选键但没有有效选择时，后续保存仍须先补齐选择，不会为了兼容而绕过校验。

例如，已采用新版快照的 `dev/order` 默认主地址从 A 更新到 B：整组未修改时改用 B；用户此前选过备用地址 C 时继续选择 C，B 只作为未选中候选补入；用户删除整个 order 组时保持删除。这里的“未修改”也比较备注，单独修改备注同样视为用户覆盖。

## 备份与降级

旧 SharedPreferences 只反映升级前状态，不含 1.1 的新环境和后续编辑。直接降级会回到升级前地址，不能保证保存最新选择。没有提供自动双向迁移工具；需要降级时，先由宿主导出当前 `snapshot().effectiveUrls()` 和候选，再在旧版显式导入，或明确接受恢复升级前备份。

不要删除文件后声称已恢复用户数据。删除、清空或替换持久化数据前核实应用包名、设备与备份内容。

旧版的地址来源可以完全是 `assets/base_urls_config.json` 的固定数组，代码 provider 只是可选覆盖方式。新版 Demo 也采用固定文件配置：Debug 包含三套示例，Release 的同名 JSON 只保留生产。旧版未显式指定键时使用的是**库模块**的 BuildConfig.DEBUG，不能保证等同于宿主构建类型；新版不再依赖这项推断。完整路径、优先级及覆盖升级的区别见 [构建配置说明](configuration.md#debug--release-打包使用哪份配置)。
